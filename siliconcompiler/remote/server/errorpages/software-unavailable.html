software-unavailable

No image provides that software

422 Unprocessable Content https://siliconcompiler.com/server-errors/software-unavailable

No live image on this deployment satisfies the job’s software requirements — a SiliconCompiler version, a Python library, or a tool version. The body lists every requirement that failed, each with what the images do hold, so you can ask for something that exists. A SiliconCompiler version no image offers is this type too, naming siliconcompiler: it covers what version-skew meant at create, which is retired.

What to do

  1. Read reason. unavailable: the requirements listed are held by no image at all, SiliconCompiler’s own version included. combination: each is held by some image, and no single image holds them together. uninstallable: while staging, the job’s Python packages cannot be installed for a target — nothing in a package’s release line installs for it, or a requirement needs another version of a distribution the image holds; available is [] and detail names each package, its version and the target Python and platform, or the host. A package no configured index has is not this: the job is sent back for its wheel. unknown_class: while staging, a node runs a task class the job’s resolved environment does not provide; unresolved names each as <module>/<Class> and detail names the node. A task’s own setup runs on the node, so it is never run as its base class instead. An unrecognised value means act on the type alone.
  2. Read unresolved: one entry per failed requirement, with requirement — your alternatives, exactly as sent — and available, the versions this deployment’s images hold. An empty available means none holds it.
  3. For unavailable, ask for a version in available. For combination, choose versions that exist in one image together.
  4. GET /v1’s software lists what is on offer before you submit, name by name. It cannot show which names share an image, which is why combination exists.

Present but reports no version. A tool an image holds but that does not report its version is listed under the date the image was published, and such an entry satisfies no version requirement. If the name is in available and you still got this, ask for it without a version.

Member
reasonREQUIRED unavailable, combination, uninstallable or unknown_class.
unresolvedREQUIRED A list of {name, requirement, available}, one per requirement that failed. requirement is the list of alternatives as sent — a requirement is met if any one resolves — and available what the live images hold; [] if none.
trace_idoptional The request’s W3C trace id. Quote it in a support request.

detail is prose and may be reworded at any time. Branch on type, and read the members above for the specifics — never parse detail.

Where it comes from

POST /v1/jobs The descriptor’s requested_versions cannot be met, a requested_versions.python name no live image holds included.
while staging The flow the manifest’s read reports cannot be placed — a job missing two tools lists both — unknown_class, and uninstallable when the job’s Python packages are installed. The job is rejected, and this is the type of its error on GET /v1/jobs/{id}.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the request’s W3C trace id: the one your client’s traceparent carried, where it sent one, so your own logs can find it too.
  • Where this arrived on a job’s error rather than on a request, there is no trace_id: quote the job’s id, the one identifier that finds the run.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

resource-unavailable is the same answer for data rather than images: a PDK, library or FPGA device this deployment does not hold and cannot supply.

declared-mismatch is a manifest whose SiliconCompiler version does not satisfy the job’s own requested_versions.python.siliconcompiler: the job asked for one version and sent another.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
