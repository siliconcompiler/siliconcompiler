software-unavailable

No image provides that software

422 Unprocessable Content https://siliconcompiler.com/server-errors/software-unavailable

No live image on this deployment satisfies one of the job’s software requirements — a SiliconCompiler version or a tool version. The body says which requirement failed and what the images do hold, so you can ask for one of those instead.

What to do

  1. Read requirement: it is the one that failed.
  2. Read available: the versions this deployment’s images hold for that name. An empty list means none hold it at all.
  3. Ask for one of those, or ask the operator for the version you need.
  4. GET /v1’s software lists what is on offer before you submit.

Present but reports no version. A tool an image holds but that does not report its version is listed under the date the image was published, and such an entry satisfies no version requirement. If the name you asked for is in available and you still got this, ask for it without a version.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/software-unavailable",
  "title":    "No image provides that software",
  "status":   422,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "requirement": "openroad>=3.0",  // REQUIRED on this type
  "available": ["2.0.1", "2.0.0"],  // REQUIRED on this type
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
Member
requirementREQUIRED The requirement no image satisfies: the name and the version specifier you sent.
availableREQUIRED What the live images hold for that name. It may be empty.
trace_idoptional The same W3C trace id as the response header. Quote it in a support request.

detail is prose and may be reworded at any time. Branch on type, and read the members above for the specifics — never parse detail.

Where it comes from

POST /v1/jobs The descriptor’s requires cannot be met.
POST /v1/jobs/{id}/submit The flow re-derived from the manifest cannot be placed.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

unsatisfiable-request is software this deployment does not have in any version.

version-skew is your client’s own version being refused.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
