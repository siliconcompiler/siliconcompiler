version-skew

Unsupported client or software version

422 Unprocessable Content https://siliconcompiler.com/server-errors/version-skew

The version of SiliconCompiler your client runs, or a version the job asks for, is not one this deployment accepts. The detail says what it runs.

What to do

  1. Compare your version with GET /v1’s software.
  2. Install a version the server accepts, or submit to a deployment that runs yours.
  3. A manifest written by a newer SiliconCompiler than the server runs is refused the same way: the server cannot read it faithfully.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/version-skew",
  "title":    "Unsupported client or software version",
  "status":   422,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

POST /v1/jobs The descriptor’s versions.
POST /v1/jobs/{id}/submit The uploaded manifest’s schema version.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

software-unavailable is a tool or framework version no image holds, not your client being refused.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
