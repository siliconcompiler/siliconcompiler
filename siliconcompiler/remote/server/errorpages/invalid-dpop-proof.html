invalid-dpop-proof

Invalid DPoP proof

401 Unauthorized https://siliconcompiler.com/server-errors/invalid-dpop-proof

The DPoP header on this request was missing, malformed, already seen, or signed by a key that is not the one your token is bound to.

HTTP/1.1 401 Unauthorized
WWW-Authenticate: DPoP error="invalid_dpop_proof"
Content-Type: application/problem+json

What to do

Fail and surface it. Do not refresh, and do not retry — retrying reproduces it, and a retry loop here reads from the server as a brute-force attempt against the key binding.

This is nearly always a client bug. Work through the proof in this order.

Check
Is there a proof at all? Every authenticated request needs one. A DPoP-bound token sent with only an Authorization header fails here.
htm and htu Must match this request’s method and URI. htu excludes the query string and fragment.
iat Within ±60 seconds. A host with a drifting clock fails every request.
jti Unique per proof. Reusing one is a replay and is refused even if everything else is correct.
The signing key Its thumbprint must equal the cnf.jkt claim in your access token. A client that regenerated its key pair but kept the old token lands here.
The nonce If the server asked for one, use it — but that is a different error, below.

Also at the token endpoint

This is raised at POST /v1/auth/token too, on grant_type=refresh_token. The refresh requires its own proof, and its thumbprint must match the one the token family was bound to at login.

That is deliberate and worth understanding: without it, every ordinary request would be key-bound except the one that mints the next credential — which is the only one worth stealing.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/invalid-dpop-proof",
  "title":    "Invalid DPoP proof",
  "status":   401,
  "detail":   "The proof's htu does not match the request URI.",
  "instance": "/v1/jobs",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

No required extension members. detail will usually name which check failed — useful while debugging, and not something to branch on.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

Four 401 conditions share this status and want opposite reactions. The status alone is not enough — branch on the WWW-Authenticate error= parameter and, for invalid_token, on the body’s type.

error=Do
invalid-dpop-proofinvalid_dpop_proof Fail — you are here.
(no type)use_dpop_nonce Retry immediately with the DPoP-Nonce just supplied. Cache it per origin — the authorization server and resource server have separate nonce spaces.
invalid-tokeninvalid_token Refresh once, then retry.
session-endedinvalid_token Re-authenticate, never refresh. Same header value — only the body’s type tells them apart.

A client that reads only the header is correct on three of these and loops forever on the fourth.
