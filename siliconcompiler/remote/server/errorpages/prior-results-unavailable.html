prior-results-unavailable

Those earlier results cannot be used

422 Unprocessable Content https://siliconcompiler.com/server-errors/prior-results-unavailable

A run that starts part-way through its flow takes the results of a node it does not run from an earlier job, named in create’s continues_from. One of those entries names results that cannot be used: step, index and job_id say which, and reason says why.

What to do

  1. Read reason. not_found, not_owner, deleted, not_completed, expired or withheld: those results are not available, so run from an earlier step — one whose results you have — or name a job of your own whose results can be used.
  2. For not_completed, name the job that ran the node: a job that only copied a node’s results in did not run it.
  3. An archived job may be continued from: archived is registered and never raised.

Member
step, indexREQUIRED The node whose results were to be copied.
job_idREQUIRED The job the entry named.
reasonREQUIRED not_found — no such job, or one you cannot read: one answer for both, so it confirms nothing. not_owner — a job you can read and do not own. deleted — the job is deleted. not_completed — that job did not complete that node, or only copied it in. expired — the artifact holding the node’s outputs, or its manifest, has been deleted. withheld — an administrator withheld one of them. archived is registered and never raised. An unrecognised value means act on the type alone.
trace_idoptional The request’s W3C trace id. Quote it in a support request.

detail is prose and may be reworded at any time. Branch on type, and read the members above for the specifics — never parse detail.

Where it comes from

POST /v1/jobs Every entry is checked before anything is uploaded.
GET /v1/jobs/{id} As a rejected job’s error: every entry is checked again while the job stages, and its results can go, or be withheld, in between.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the request’s W3C trace id: the one your client’s traceparent carried, where it sent one, so your own logs can find it too.
  • Where this arrived on a job’s error rather than on a request, there is no trace_id: quote the job’s id, the one identifier that finds the run.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

archive-rejected with reason: "missing_member" is a node the run reads whose results the client sent neither in the archive nor as a job in continues_from.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
