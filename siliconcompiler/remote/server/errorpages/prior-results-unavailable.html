prior-results-unavailable

Those earlier results cannot be used

422 Unprocessable Content https://siliconcompiler.com/server-errors/prior-results-unavailable

A run that starts part-way through its flow takes the results of a node it does not run from an earlier job, named in create’s continues_from. One of those entries names results that cannot be used: step, index and job say which, and reason says why.

What to do

  1. Read reason. archived: unarchive the job and submit again. not_found, deleted, not_completed, expired or withheld: those results are not available, so run from an earlier step — one whose results you have, or can take from a job that still holds them.
  2. For not_completed, name the job that ran the node: a job that only copied a node’s results in did not run it.

Member
step, indexREQUIRED The node whose results were to be copied.
jobREQUIRED The job the entry named.
reasonREQUIRED not_found — no such job, or not yours: one answer for both, so it confirms nothing. deleted — the job is deleted. archived — the job is archived; unarchiving it fixes this. not_completed — that job did not complete that node, or only copied it in. expired — the artifact holding the node’s outputs, or its manifest, is gone. withheld — an administrator withheld one of them.
trace_idoptional The same W3C trace id as the response header. Quote it in a support request.

detail is prose and may be reworded at any time. Branch on type, and read the members above for the specifics — never parse detail.

Where it comes from

POST /v1/jobs Every entry is checked before anything is uploaded.
POST /v1/jobs/{id}/submit Checked again: the job can be archived, or its artifacts reaped, in between.
GET /v1/jobs/{id} As the job’s error.type, reason: "expired", when the results went before staging could copy them. The job is rejected.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

archive-rejected with violation: "missing_member" is a node the run reads whose results the client sent neither in the archive nor as a job in continues_from.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
