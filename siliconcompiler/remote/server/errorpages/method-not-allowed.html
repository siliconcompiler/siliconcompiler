method-not-allowed

Method not allowed

405 Method Not Allowed https://siliconcompiler.com/server-errors/method-not-allowed

The path exists, and not for the method you used. The response carries an Allow header listing the methods it does take.

What to do

  1. Read Allow and use one of those methods.

An untyped answer is expected here. This refusal is often produced below the request handler — by routing, the framework or a proxy — and then it arrives as the web server’s own page, not as application/problem+json, and has no type at all. Treat a non-problem+json 405 exactly as you would this type.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/method-not-allowed",
  "title":    "Method not allowed",
  "status":   405,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

any endpoint Routing.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the request’s W3C trace id: the one your client’s traceparent carried, where it sent one, so your own logs can find it too.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

At the two OAuth endpoints

Raised at POST /v1/auth/token and POST /v1/auth/device too, before any OAuth processing, and in problem+json there as everywhere — never as an OAuth error. A client handles it by its status and type.

What this is not

not-found is a path, or a thing, that is not there for you at all.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
