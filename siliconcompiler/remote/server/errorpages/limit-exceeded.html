limit-exceeded

Limit exceeded

429 Too Many Requests https://siliconcompiler.com/server-errors/limit-exceeded

You have reached a published ceiling on how much you may have going at once — jobs, uploads, open log streams, devices. Each of these refills as what you already have finishes, or, for a device, when you revoke one.

What to do

  1. Read limit. It is the exact key published in limits — GET /v1’s, or your account’s in GET /v1/me — so you can compare it with what you hold.
  2. Wait for Retry-After, then send the same request again.

Formerly four separate types, each of which a client may still have in its code: quota-exhausted, pending-upload-limit, concurrent-job-limit and concurrent-stream-limit. They are one type now, and limit says which. max_download_bytes was briefly answered here too, and moved to its own type because it does not refill.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/limit-exceeded",
  "title":    "Limit exceeded",
  "status":   429,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "limit":    "concurrent_jobs",  // REQUIRED on this type
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
Member
limitREQUIRED The published key that bound: concurrent_jobs, pending_uploads, concurrent_log_streams or devices. The usage keys — compute_seconds, storage_bytes, licence_seconds — are registered and not raised today: nothing checks the compute quota at create or at submit.
trace_idoptional The same W3C trace id as the response header. Quote it in a support request.

detail is prose and may be reworded at any time. Branch on type, and read the members above for the specifics — never parse detail.

Where it comes from

POST /v1/jobs pending_uploads: too many jobs created and not yet submitted.
POST /v1/jobs/{id}/submit concurrent_jobs: too many jobs queued or running.
the log stream concurrent_log_streams: too many live logs open at once.
enrolling a device devices: more machines enrolled than your account allows. Revoking one with DELETE /v1/devices/{id} frees its place.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

node-limit-exceeded, upload-too-large and download-too-large are ceilings that do not refill: the request itself is too big, and waiting changes nothing.

rate-limited is about how often you call, not what you hold; it names no limit.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
