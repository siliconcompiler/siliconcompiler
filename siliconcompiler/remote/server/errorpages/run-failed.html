run-failed

The run failed

Not an HTTP response https://siliconcompiler.com/server-errors/run-failed

The run itself failed. The job was accepted and ran, and a node — or the run around the nodes — ended in failure.

What to do

  1. Look at the nodes: the one whose error_type is this, and whose exit_code is non-zero, is where it happened.
  2. Read that node’s log. Where no node failed, the job’s own log says why the run stopped.

The body

{
  "id":    "01J9...",
  "state": "failed",
  "error": {
    "type":   "https://siliconcompiler.com/server-errors/run-failed",
    "title":  "The run failed",
    "detail": "..."
  }
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

GET /v1/jobs/{id} As the job’s error.type, and as error_type on each failed node.

Getting help with your specific failure

This type arrives inside a job, not on a request, so there is no trace_id on it. Quote the job’s id when you escalate — it is the one identifier that finds the run on the server, its scheduler job and its logs.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your job — the job id is what connects the two.

What this is not

scheduler-lost is a run that went away without ending.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
