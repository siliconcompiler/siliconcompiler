Not acceptable

406 Not Acceptable https://siliconcompiler.com/server-errors/not-acceptable

Your Accept header asks for nothing this endpoint can produce. Most of this API ignores Accept and sends its one representation, so this is rare.

What to do

  1. Accept application/json on the API, and text/event-stream at the log stream.

An untyped answer is expected here. This refusal is often produced below the request handler — by routing, the framework or a proxy — and then it arrives as the web server’s own page, not as application/problem+json, and has no type at all. Treat a non-problem+json 406 exactly as you would this type.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/not-acceptable",
  "title":    "Not acceptable",
  "status":   406,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

any endpoint Content negotiation, where a deployment does it.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

unsupported-media-type is about what you sent, not what you accept.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
