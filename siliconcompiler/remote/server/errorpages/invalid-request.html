invalid-request

Invalid request

400 Bad Request https://siliconcompiler.com/server-errors/invalid-request

The request was malformed: a body that does not validate, a missing or contradictory parameter.

What to do

  1. Read detail for which field.
  2. Fix the request; the same request returns the same answer.

An untyped answer is expected here. This refusal is often produced below the request handler — by routing, the framework or a proxy — and then it arrives as the web server’s own page, not as application/problem+json, and has no type at all. Treat a non-problem+json 400 exactly as you would this type.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/invalid-request",
  "title":    "Invalid request",
  "status":   400,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

any endpoint Request validation.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

invalid-cursor is specifically a bad pagination cursor.

unsupported-media-type is a body of the wrong type.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
