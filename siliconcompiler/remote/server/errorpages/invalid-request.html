The request was malformed: a body that does not validate, a missing or contradictory parameter, or a request member or query parameter this contract does not define — which is refused, never ignored, so a misspelled filter cannot read as an answer.

At POST /v1/auth/token and POST /v1/auth/device a malformed request is invalid_request, in the OAuth shape, and an unknown parameter is ignored — except actor_token, audience and resource, which are refused invalid_request.

What to do

  1. Read detail for which field.
  2. Fix the request; the same request returns the same answer.

An untyped answer is expected here. This refusal is often produced below the request handler — by routing, the framework or a proxy — and then it arrives as the web server’s own page, not as application/problem+json, and has no type at all. Treat a non-problem+json 400 exactly as you would this type.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/invalid-request",
  "title":    "Invalid request",
  "status":   400,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

any endpoint Request validation.
POST /v1/jobs A descriptor.sources entry whose keypath is not a dataroot in one of the two places SiliconCompiler keeps one: ["library", name, "dataroot", root], or a task’s own, ["tool", tool, "task", task, "dataroot", root]. The server does not guess what owns a dataroot. An entry carrying name or dataroot, the members keypath replaced, is refused as any unknown member is.

What this is not
