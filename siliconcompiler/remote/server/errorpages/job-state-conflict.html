job-state-conflict

The job is not in a state that allows this

409 Conflict https://siliconcompiler.com/server-errors/job-state-conflict

The job’s current state does not allow the call you made. That is one of three things: a submit that is not a replay of the original, or an upload grant, for a job past awaiting_input; an upload-grant re-issue naming a different bytes from the one the archive’s first grant fixed; or DELETE of a job that is not terminal.

What to do

  1. Read the job with GET /v1/jobs/{id} to see its state.
  2. A retried submit that already succeeded is not this: replay it with the same Idempotency-Key and the same body, and you get the original response back.
  3. Re-issue a grant with the bytes the archive’s first grant fixed. A re-issue cannot change the size.
  4. To delete a job that is still going, cancel it with POST /v1/jobs/{id}/cancel and delete it once the job object says it is terminal.

The body

{
  "type":     "https://siliconcompiler.com/server-errors/job-state-conflict",
  "title":    "The job is not in a state that allows this",
  "status":   409,
  "detail":   "...",
  "instance": "/v1/jobs/01J9...",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

detail is prose and may be reworded at any time. Branch on type — never parse detail.

Where it comes from

POST /v1/jobs/{id}/upload-grant The job is not in created or awaiting_input, or a re-issue names a different bytes from the grant already fixed.
POST /v1/jobs/{id}/submit The job is past awaiting_input, and this is not a replay of the original submit.
DELETE /v1/jobs/{id} The job is not terminal. Cancel a running job first; an administrator is held to this too.

Getting help with your specific failure

Two members of the body identify your exact request. Quote both when you escalate — with them, whoever helps you finds the one request instead of searching a five-minute window.

  • trace_id — the correlation id. The same value is on the response as a header, so it is in your logs even if the body is not.
  • instance — the request this happened to.

This page documents the error type. It is the same page for everyone who hits it and it cannot see your response — trace_id is what connects the two.

What this is not

not-ready is also a 409, and transient: an output that is on its way, with a Retry-After to wait for. This one carries no Retry-After: the identical call gets the identical answer, unless something else has moved the job on — a cancel finishing, for a DELETE.

not-found (404) is a job that does not exist or is not yours. A 409 means the job is established and its state is the problem.

idempotency-key-reuse (422) is a key sent again with a different request. A true replay of the original submit is answered with the original response, not with either.

Normative definition: the error type registry in the SiliconCompiler v1 API contract. This page is a rendering of it — where the two disagree, the registry is right.
