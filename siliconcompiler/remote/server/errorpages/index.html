server-errors

Every failure a SiliconCompiler v1 orchestrator can return

Every error from a SiliconCompiler-compatible orchestrator is an RFC 9457 application/problem+json body, and its type is a URI under this path. You are probably here because you dereferenced one.

{
  "type":   "https://siliconcompiler.com/server-errors/entitlement-denied",
  "title":  "Not entitled to this resource",
  "status": 403,
  ...
}

Clients branch on type and nothing else. title and detail are prose and may be reworded in any release — a client that string-matches them is broken by a typo fix. The type URI is frozen for the life of v1.

Not every failure has a type. The guarantee covers what a /v1 request handler produced. A stopped process, a proxy refusing an oversized body, or a routing-level rejection can answer first, with the web server’s own HTML. Inspect Content-Type, treat a non-problem+json non-2xx as an untyped failure of its status class, and never assume type exists. A client doing resp.json()["type"] on any non-2xx throws on the errors it is most likely to meet in production.

Stability

The registry is frozen at v1. A type may gain extension members — that is additive, and an unrecognised member is ignored, never an error. Changing what a member means, or retiring a URI, costs a major version.

The URIs are identical on every deployment, whether you are talking to the reference sc-server or a commercial orchestrator. That is the property the registry exists for: a client switching between them needs one table, not two.

The normative source is the error type registry in the SiliconCompiler v1 API contract. These pages are a rendering of it.
